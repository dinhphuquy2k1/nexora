# API contract

## Current Identity and MFA contract — Logical PR6

Current Logical PR6: OPERATOR authenticates with local password and receives a PASSWORD session; ADMIN receives only a pending challenge after password and must complete TOTP or single-use recovery verification for an MFA session. All admin APIs require database-backed ADMIN+MFA. Uniship is independent of identity. Public activation still requires actual deployment evidence; the explicit profile is implemented by NEXORA-024. Shipment sync remains PLANNED. See the PR6 contract amendment below and NEXORA-022 verification evidence.

Generated OpenAPI/SDK describe the implemented routes below. Error responses use `{code,message,requestId}`. Every administrative route requires an ACTIVE ADMIN database-backed MFA session; all mutations require a trusted Origin. Missing/revoked/disabled sessions return 401 `UNAUTHORIZED`; OPERATOR callers return 403 `FORBIDDEN`. Origin failures retain 403 `FORBIDDEN`, and shared admission rejection retains 429 `TOO_MANY_REQUESTS` for compatibility.

| :----------------------------------------- | :----------------------------------------------- | :----------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| POST `/api/auth/login`                     | `{username,password}`                            | 200 OPERATOR `{user:{id,username}}` + session; ADMIN `{mfaRequired:true}` + pending cookie | 400 `VALIDATION_ERROR`, 401 `AUTHENTICATION_FAILED`, 403, 429                                   |

`ManagedUser` has exactly `id,username,role,status,hasPassword,createdAt,updatedAt`; hashes and tokens are excluded. The owner approved the status/list contract on 2026-10-15 (`USER_STATUS_ADMIN_CONTRACT`, NEXORA-016). ADMIN may change an OPERATOR, another ADMIN or itself, preserving the last ACTIVE ADMIN. Disable revokes all sessions, pending MFA challenges and pending setup tokens atomically; reactivation restores none. Self-disable revokes its own sessions. Role changes are unsupported.

Setup passwords require 8–1024 characters before Scrypt. Links contain 256-bit CSPRNG secrets as `/setup#token=<secret>` on the request's configured trusted origin; only SHA-256 is stored, TTL is 24 hours. Reissue invalidates all old unconsumed links and rejects configured users. Setup never resets an existing credential or automatically logs in. Link responses use `Cache-Control: no-store`.

`POST /api/auth/provider/login` is removed, always returns 404 regardless of Uniship configuration, and is absent from generated contracts. The owner-approved upgrade migration revokes all sessions of credentialless OPERATOR users; ADMIN/configured OPERATOR sessions remain. Deleted tokens cannot regain validity after setup. The upgrade did not change the historical session transport; current PR6 administrative assurance is described below.

## Carrier Connections Management — implemented PR 3 / PR 4

Endpoints strictly enforce ownership from the authenticated session (`user_id`). Users cannot access, mutate, or inspect other users' carrier connections. All protected carrier endpoints enforce `401 UNAUTHORIZED` if the caller's session is missing or expired.

PR3 GET/PATCH/DELETE and PR4 POST/create/reconnect are IMPLEMENTED (backend only). Provider summaries have exactly `provider,displayName`; the single `uniship` entry advertises metadata vocabulary, not live readiness. Connection summaries have exactly the eight fields listed below. GET ignores query ownership selectors: the database predicate always uses the authenticated user ID. PATCH accepts only displayName (1–100 characters, trimmed nonblank); invalid UUID/body returns 400 VALIDATION_ERROR. DELETE also validates UUID (400). Both mutations enforce OriginGuard (403 FORBIDDEN), and return 404 NOT_FOUND for absent/foreign connections, including ADMIN callers. DELETE hard-deletes with secret cascade and returns `{success:true}`. All metadata responses use no-store.

- **Payload Safety**: Connection DTOs expose only metadata (`id, provider, externalAccountId, loginIdentifier, displayName, status, lastVerifiedAt, createdAt`). Plaintext passwords, tokens, nonces, and ciphertexts are never returned.
- **Unified Generic Error Policy (`CANNOT_CONNECT_CARRIER_ACCOUNT`)**: On `POST /api/carrier-connections`, Nexora returns the identical generic error `400 CANNOT_CONNECT_CARRIER_ACCOUNT` ("Không thể kết nối tài khoản này") for BOTH invalid provider credentials and duplicate account linkage (`UNIQUE(provider, external_account_id)`). This completely obscures whether the carrier credentials were valid, whether the carrier account was already linked to another user, or who the existing owner is. Detailed causes (`PROVIDER_AUTH_FAILED` vs `DUPLICATE_EXTERNAL_ACCOUNT`) are recorded strictly in the server-side security audit log.
- **Protected Carrier Endpoints & 401 UNAUTHORIZED**: Every carrier management endpoint requires a valid active Nexora session. Missing, expired, or revoked sessions return `401 UNAUTHORIZED`.
- **Conditional Login Identifier**: `loginIdentifier` is conditional per adapter and nullable at the schema level; providers without username/email credentials (e.g. OAuth/API key) do not require it.
- **Rate Limiting**: `POST /api/carrier-connections` and `reconnect` enforce per-user burst and window limits to prevent credential stuffing attacks against carrier infrastructure.

## Contract Generation & Verification

All responses carry server-generated `x-request-id`; HTTP errors contain code/message/requestId and do not expose stack, SQL or credentials. Unknown paths return 404 NOT_FOUND. Swagger is off by default, explicitly enabled via API_DOCS_ENABLED=true.
`contracts:generate` compiles a documentation-only Nest module with the SAME health controller/decorators, never listens and never requires a DB/storage connection, writes OpenAPI then runs openapi-typescript. `packages/sdk` uses openapi-fetch over generated paths; both types and client behavior follow OpenAPI rather than importing API code.
`contracts:check` compares content and the complete generated file set before/after regeneration, then checks Git status including untracked paths when Git/HEAD are available. Both OpenAPI and SDK generators clean only their owned output directories; file-set comparison works without Git in minimal Docker images, and an unexpected new generated file triggers drift. Outputs are committed. Build does not silently regenerate them.
Breaking contract changes require consumer/tests/docs together. Monetary JSON fields in later endpoints are decimal strings.

Login runtime input accepts a JSON object with string `username` and `password`. Username is trimmed, case-sensitive, 3–50 characters; password is nonempty and at most 1024 characters. Null, arrays, invalid types and length violations return `400 VALIDATION_ERROR` before lookup/Scrypt. Origin enforcement and cookie policy are owned by [Configuration](../operations/configuration.md). Successful logout clears the cookie only after revocation; unexpected database failure uses the existing safe `500 INTERNAL_ERROR` envelope. No DTO or generated schema changes are required by these boundary checks.

Published authentication failures reference the existing `ApiErrorDto` JSON schema (`code`, `message`, `requestId`): Login 400/401/403/429, session 401, and Logout 403/500. Generated SDK consumers can inspect these response bodies without escaping generated types. This schema correction changes no runtime statuses, error codes, messages or request ID behavior.

### PR4 lifecycle details — NEXORA-018

Both POST mutations require OriginGuard (403 FORBIDDEN), an ACTIVE owner session and no-store responses. Connect requires exactly provider, loginIdentifier, password, displayName; uniship requires a trimmed nonblank identifier of at most 128 characters, trimmed nonblank displayName of at most 100, and an unchanged password of 1..1024 characters. Client userId/externalAccountId/token/status and unknown fields are rejected 400. Reconnect accepts password only and a UUID; foreign/missing connection returns 404, including for ADMIN. Successful201/200 results contain the same eight metadata fields, never secrets/versions/epochs.

Every login token is verified using the observed verify contract, with coherent login/verify userid; only verified userid supplies external identity. Identity mismatch requires manual reconnect and preserves previous ciphertext. Invalid credentials and duplicate external account share exactly 400 CANNOT_CONNECT_CARRIER_ACCOUNT / "Không thể kết nối tài khoản này"; safe audit reasons distinguish them internally. Reconnect provider rejection or identity mismatch returns 401 PROVIDER_AUTH_FAILED. Temporary provider/crypto/audit/stale-result failure returns 503 SERVICE_UNAVAILABLE; local admission/provider429 returns 429 RATE_LIMITED. Other Identity admission retains its existing TOO_MANY_REQUESTS code. Unknown expiry is null, JWT exp is scheduling only, no fixed TTL or refresh endpoint. No public endpoint triggers lazy recovery or reads decrypted secrets. External live execution is hard-closed pending official provider evidence; generated SDK presence does not imply live readiness.

### Provider-conditional loginIdentifier — NEXORA-019

The generic connect shape above uses loginIdentifier? because requirements depend on the provider's authentication protocol. The current only provider, Uniship, requires a trimmed nonblank username of at most128 characters. Its current ConnectCarrierDto/OpenAPI/SDK therefore correctly mark loginIdentifier required. Missing, blank, null, oversized, unknown-provider and extra-field payloads return400 VALIDATION_ERROR before provider work. Database/metadata loginIdentifier remains nullable for future providers. A future OAuth/API-key provider that needs no username/email will get its own request schema when implemented; no union framework or new provider is added now.

### Manual reconnect failure semantics — owner-approved 2026-10-16

POST /api/carrier-connections/:id/reconnect is a non-destructive replacement attempt. Wrong new password returns401 PROVIDER_AUTH_FAILED while preserving the previous status, complete encrypted credentials and lastVerifiedAt. Temporary timeout/5xx returns503 SERVICE_UNAVAILABLE;429 retains RATE_LIMITED/backoff; both preserve prior state. Candidate verification rejection or login/verify identity inconsistency also returns the existing safe401 and preserves the old connection. An already REAUTH_REQUIRED or ERROR connection retains that status on these failures. Only coherent verified userid different from the stored account requires REAUTH_REQUIRED; successful matching replacement atomically sets CONNECTED. Failure audit remains metadata-only. Claim/version increments are internal and may still occur; lastVerifiedAt changes only after successful verification/persistence.

No new public error, endpoint, DTO or identity disclosure is introduced. New-connect authentication/identity failures retain generic400 CANNOT_CONNECT_CARRIER_ACCOUNT. Internal automatic recovery keeps fail-closed REAUTH_REQUIRED for unusable stored credentials/identity failure and ERROR/backoff for temporary provider failures; crypto and audit gates remain unchanged. See the dated ADR-007 clarification and NEXORA-020 regression evidence.

### Internal superseded recovery — NEXORA-021

No endpoint, DTO, generated contract or public error is added. Lazy recovery re-evaluates owner/status and committed token evidence after supersession; a failed manual claim does not make an expired/rejected token usable. A newer eligible token is reused. Repeated contention or exhausted recovery budget uses the existing safe503 SERVICE_UNAVAILABLE mapping for internal STALE. Internal sealed-token revision/outcomes are never public fields or audit metadata. Manual reconnect and automatic failure semantics above remain unchanged.

## Mandatory ADMIN MFA — Logical PR6/NEXORA-022

POST /api/auth/login retains local credentials and Origin/no-store.200 response is one of {user:{id,username}} for OPERATOR with nexora_session, or {mfaRequired:true} for ADMIN with only a pending challenge (an existing session cookie is cleared). Correct-password ADMIN without enrollment receives403 MFA_ENROLLMENT_REQUIRED with trusted CLI guidance; incorrect passwords retain401 AUTHENTICATION_FAILED without enrollment disclosure. Raw challenge is exclusively nexora_mfa_token: HttpOnly,SameSite=Strict,Path=/api/auth/mfa,Max-Age300,Secure=false for supported loopback HTTP.

POST /api/auth/mfa/verify is Public only with respect to session authentication; Origin and pending cookie are mandatory. Strict JSON has exactly type and code, for example `{ "type": "totp", "code": "123456" }` or `{ "type": "recovery", "code": "01234567-89ABCDEF-01234567-89ABCDEF" }`; TOTP is six ASCII digits, recovery format is four groups of eight hexadecimal characters separated by hyphens, case normalized server-side. No client token/authLevel fields.200 {user:{id,username}} sets nexora_session only after committed challenge/proof consumption and session insertion and clears pending cookie.400 VALIDATION_ERROR,401 MFA_VERIFICATION_FAILED (invalid/expired/replayed challenge or proof),403 FORBIDDEN Origin,429 TOO_MANY_REQUESTS, generic500 crypto/database failure. No challenge or secret/hash appears in responses. All responses including failures are no-store.

POST /api/auth/mfa/cancel uses Public+Origin, revokes the presented pending cookie's challenge and clears its scoped cookie after successful database work,200 {success:true}; invalid/missing cookie is idempotent. No enrollment/reset endpoint. Logout keeps its existing session revocation contract. Cancelling the second step does not create a session.

### Pending cancellation versus authenticated logout

The pending cookie Path=/api/auth/mfa means compliant browsers send it to verify/cancel, but not /api/auth/logout. Cancel identifies only the presented token hash, locks its owning user before targeted deletion and clears the scoped cookie after commit. Missing, invalid, expired or already-cancelled tokens are safe/idempotent; unexpected database failure propagates safe500 INTERNAL_ERROR without clearing the cookie. Cancellation does not consume a TOTP step/recovery code or revoke unrelated challenges/sessions. Verify and cancel serialize on the same user lock: verify-first may validly issue a session that cancel does not revoke; cancel-first prevents session issuance.

AccountMenu logout revokes only the presented authenticated session and clears nexora_session after successful persistence. It cannot identify or revoke a pending challenge from the scoped cookie. A browser with both cookies therefore retains its pending challenge after session logout; the remaining second factor is still mandatory, and the five-minute expiry remains. This is the accepted separate-operations contract, not unified atomic termination. No additional owner approval or ADR scope amendment is needed to preserve it.

Tabs share cookies within the same browser profile. Later ADMIN password success replaces the browser's pending cookie; older pending rows follow the existing maximum-five retention/expiry policy. Cancel targets the currently presented cookie only. Cancel/back stays on the MFA form on network/database failure and returns to the password form only on success. No pending token is exposed to JavaScript, bodies or URLs. Unified termination would require a separately reviewed design; two requests would not be atomic.

All /api/admin/... APIs require active ADMIN role plus persisted session.auth_level=MFA globally; PASSWORD assurance returns403, missing/expired/revoked sessions401. Client body/header/cookie assurance values are never trusted. Existing seven-field user administration summaries and Carrier metadata remain unchanged. Normal workspace accepts a valid ACTIVE PASSWORD or MFA session. OpenAPI/SDK are regenerated with no raw challenge field.
