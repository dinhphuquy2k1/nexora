## 2. Requirements & Boundary Scope

### 2.1 Core Objectives

Execute a complete, faithful frontend migration of Nexora from the reference ZIP archive (`nexora-logistics-management (1).zip`), replacing existing UI presentation, component styling, typography, responsiveness, and interaction flows while strictly preserving:

1. Nexora's Next.js 16 App Router architecture and server-side routing model.
2. Centralized CSS Modules and design tokens in `apps/web/styles/tokens.css`.
3. Native local session authentication, HttpOnly cookies, CSRF protection via OriginGuard, server-side workspace authorization guard in `apps/web/app/(workspace)/layout.tsx`, and TOTP/recovery MFA for ADMIN roles.
4. Authoritative backend domain boundaries, Tactical DDD invariants, and OpenAPI transport contracts via `@nexora/sdk`.
5. Honest presentation of unimplemented backend capabilities: zero mock production records, zero fake tracking events, and zero fabricated freight calculation formulas.

### 2.2 Strict Architectural & Domain Boundaries

- **Ownership Boundaries**:
  - Technical UI ownership is partitioned across Tier A (`packages/ui/`), Tier B (`apps/web/components/app-shell/`), and Tier C (`apps/web/features/`).
  - No aggregate, entity, or service logic in backend domains (`apps/api/src/customer/`, `apps/api/src/carrier/`, `apps/api/src/identity/`) is modified.
  - Zero direct database access, prisma client imports, or migration files in frontend code.
- **Dependency & Tooling Hygiene**:
  - Zero Vite or Tailwind CSS v4 runtime dependencies introduced into Nexora.
  - Zero `@google/genai` client packages or web scraping integrations.
  - Native Node.js test infrastructure and existing Chromium CDP smoke harness (`scripts/browser-login-smoke.mjs`) planned for visual/browser testing without adding Playwright or Puppeteer.
- **Pre-Code Stop Condition (ADR-009)**:
  - This review is strictly documentation-only. All implementation code, tests, dependencies, and database modifications are strictly prohibited until the repository owner posts an authenticated ADR-009 approval decision.

## 5. Tactical DDD Domain Invariants & Business Envelopes

### 5.1 Customer Domain Invariants (ADR-008)

1. **Mandatory Initial Address**: Every customer creation requires an initial recipient address (`address.addressText`).
2. **Address Cardinality**: A customer aggregate must contain at least one address (`Customer.addresses.length >= 1`).
3. **Sole Address Protection**: Attempting to delete a customer's sole address is rejected by the aggregate with HTTP 409 `LAST_CUSTOMER_ADDRESS`.
4. **Default Address Consistency**: Exactly one address must have `isDefault: true` at all times.
5. **Default Address Reassignment Sequencing**: Deleting the default address when alternative addresses exist requires explicit reassignment first via `PUT /api/customers/:id/default-address`. Direct deletion is rejected with HTTP 409 `DEFAULT_ADDRESS_REASSIGN_REQUIRED`.
6. **Phone Number Authority**: Customer phone numbers are normalized and stored in E.164 format. The backend is the sole authority for normalization and duplicate detection (`409 CUSTOMER_PHONE_EXISTS`).
7. **Sequence Code Invariance**: Customer codes are sequence-generated identifiers (`KH000001`) that cannot be edited or modified.

### 5.2 Carrier Domain Invariants (ADR-007)

1. **Single Supported Runtime Provider**: The runtime provider catalog (`CarrierService.providers()`) currently returns **only Uniship** (`{ provider: "uniship", displayName: "Uniship" }`). No other provider (GHN, GHTK, ViettelPost, J&T) is operational in the backend API.
2. **Connect Parameter Invariants**: Connecting a Uniship account requires exactly 4 keys: `provider`, `loginIdentifier` (1..128 chars), `password` (1..1024 chars), `displayName` (1..100 chars). Submitting unknown keys or non-Uniship providers is rejected with HTTP 400 `VALIDATION_ERROR`.
3. **No Credential Persistence in Client**: Plaintext passwords, tokens, or API keys are never stored in browser storage (`localStorage`, `sessionStorage`, URLs, client logs) and are never exposed in backend response DTOs. `CarrierConnectionDto` exposes metadata and nullable `loginIdentifier: string | null` without plaintext secrets. If the frontend chooses to mask a login identifier visually, it is a client presentation rule; the backend response is not inherently masked.
4. **Owner Tenant Isolation**: All carrier connections are strictly isolated by owner ID. Attempting to access or disconnect another owner's connection returns HTTP 404 `NOT_FOUND`.
5. **Connection Test Boundary**: Nexora does not implement a standalone "Test Connection" endpoint. The UI must not simulate connection testing or silently trigger re-authentication.
6. **Carrier Reconnect Frontend Classification**:
   - The backend endpoint `POST /api/carrier-connections/:id/reconnect` is implemented and functional in `CarrierLifecycleController`.
   - However, the frontend UI (`apps/web/features/carrier-connections/ReconnectModal.tsx`) is **planned for M4** and does not exist on current main.
   - Reconnect interaction is classified as `NEXORA_ADAPTATION` with delivery classification `FUNCTIONAL_WITH_EXISTING_API`, distinguishing implemented backend capability from planned frontend screens.

### 5.3 Shipment Domain Boundaries

1. **Shipment Backend V1 Unimplemented**: Nexora has not yet implemented the Shipment Aggregate backend.
2. **Truthful Planned Presentation**: Retail Packages UI must render honest empty states and mark package creation/export as planned features ("Tính năng đang được phát triển").
3. **Zero Speculative Calculations**: No hardcoded freight rates (e.g., `28,000 VND/kg`) or mock tracking timelines. Missing rates are explicitly displayed as `"Chưa có báo giá"`.

## 6. Authentication, Session & Security Architecture

### 6.1 Login Remember Me Specification (Option 1 Selected)

- **Problem**: The reference ZIP includes a "Remember Me" checkbox, but Nexora's `POST /api/auth/login` contract accepts only `{ username, password }` with a fixed 7-day session cookie TTL (`SEVEN_DAYS_MS`).
- **Options Evaluated**:
  - _Option 1 (Recommended & Selected)_: Remember non-secret username in browser `localStorage` under `nexora_remembered_username`. When checked, the username is populated on `/login` load. When unchecked upon login, the key is removed. Zero storage of passwords, tokens, or MFA secrets; zero modification to server cookie TTL.
  - _Option 2_: Remove or disable the control. (Rejected: reduces visual parity with ZIP).
  - _Option 3_: True persistent sliding sessions. (Rejected: requires backend auth contract redesign outside frontend scope).
- **Security Rule**: The frontend will never persist sensitive credentials or session tokens in `localStorage`.

### 6.2 CSRF, OriginGuard & Safe Return URL Protection

All state-mutating requests (`POST`, `PATCH`, `PUT`, `DELETE`) are protected by NestJS `OriginGuard`, requiring valid `Origin` / `Referer` headers matching the deployment policy. The frontend SDK communicates exclusively via same-origin relative `/api/*` proxies.

Current `LoginForm.tsx` reads:

```typescript
const rawFrom = searchParams.get("from");
const returnUrl = sanitizeReturnUrl(rawFrom);
```

Therefore, the canonical redirect query parameter is:

```
/login?from=<safe-relative-path>
```

References to `/login?returnUrl=...` are deprecated and replaced. Redirection through `sanitizeReturnUrl()` guarantees that external URLs, protocol-relative paths (`//evil.com`), and backslash paths are neutralized to `/`.

### 6.3 TOTP & Recovery Code MFA Authentication Flow

For ADMIN users, `POST /api/auth/login` returns `{ mfaRequired: true }` and sets a short-lived `nexora_mfa_token` cookie. The UI transitions to the MFA challenge modal, supporting both 6-digit TOTP and 32-hex recovery codes.

The authoritative DTO (`MfaVerifyRequestDto`) requires:

```typescript
type MfaVerifyRequest = {
  type: "totp" | "recovery";
  code: string;
};
```

- For TOTP verification: `{ "type": "totp", "code": "123456" }`
- For recovery code verification: `{ "type": "recovery", "code": "<valid-recovery-code>" }`

A request containing only `{ code }` without `type` is rejected by the backend validator. Pending MFA challenges can be cancelled via `POST /api/auth/mfa/cancel`. Successful verification issues the canonical `nexora_session` cookie.

**Required Test Cases Specified**:

1. OPERATOR password login succeeds without MFA challenge.
2. ADMIN login requires MFA challenge (`mfaRequired: true`).
3. Six-digit TOTP verification success and failure.
4. Recovery code verification success and failure.
5. MFA challenge cancellation via `POST /api/auth/mfa/cancel`.
6. Pending challenge expiration handling.
7. Session expiration handling.
8. Server session revocation on logout via `POST /api/auth/logout`.
9. Sanitized `from` parameter redirection.
10. Zero credentials or tokens in browser persistence.
11. Remember Me stores non-secret username only.

### 6.4 Server-Side Session Guard & Protected Workspace Authorization Boundary

The canonical session authorization boundary in Nexora is **server-side**, enforced in the root workspace layout:

```
Incoming protected workspace request
         │
         ▼
apps/web/app/(workspace)/layout.tsx
         │
         ▼ Read nexora_session HttpOnly cookie
getCachedServerSession(cookieValue)
         │
         ▼
verifyServerSession(cookieValue) in apps/web/lib/api/session.ts
         │
         ▼ Server-to-server HTTP request: GET /api/auth/session
         ├─────────────────┬───────────────────┐
         │                 │                   │
         ▼                 ▼                   ▼
 status === "authenticated"  status === "unauthenticated"  status === "unavailable"
         │                 │                   │
         ▼                 ▼                   ▼
Render <AppShell user={...}>   Extract x-pathname     Render fail-closed
                               sanitize via sanitizeReturnUrl()  service-unavailable UI
                               redirect(/login?from=...)  (No unsafe redirect loop)
```

- **Component Responsibilities**:
  - `apps/web/app/(workspace)/layout.tsx`: The **sole authoritative server authorization boundary**. Validates session token, executes server redirect, or displays fail-closed error UI.
  - `apps/web/components/app-shell/AppShell.tsx` & `ShellClient.tsx`: Pure presentation components receiving validated `user` object. They manage responsive layout state (sidebar collapse, navigation active item), **never session authorization**.
  - **Forbidden Anti-Pattern**: Adding client-side `useEffect` route guards or client session managers to `AppShell.tsx` is strictly prohibited. Protected content is never delivered to unauthenticated clients.
- **Fail-Closed Availability**: If the backend identity service is down or unreachable, the layout renders the accessible `unavailableContainer` error message (`Dịch vụ không khả dụng`) rather than triggering an infinite login redirect loop.
- **Malformed Response Handling**: If the session endpoint returns HTTP 200 with malformed JSON or `authenticated !== true`, `verifyServerSession` treats the response as unauthenticated and denies access.

### 6.5 Elimination of Insecure Quick-Fill Demo Shortcuts in Production

- The reference ZIP `LoginPage.tsx` defines `handleQuickFill`, populating demo credentials (`NXR-8829` / `12345678`).
- In Nexora's production architecture, real credentials and mandatory MFA are enforced. Demo credential shortcuts must **never** enter production or development UI code.
- Hardcoding demo passwords or credentials in UI components violates security policies ([PROJECT_RULES.md](../../ai/PROJECT_RULES.md)).
- Automated browser smoke verification utilizes isolated, disposable test users provisioned via dedicated CLI scripts (`scripts/user-create.mjs`), never static UI shortcuts.
- Interaction #9 is retained in the ZIP inventory for complete source traceability, but its target delivery classification is marked `PRODUCT_DECISION_PENDING` (policy-required exclusion; intentionally omitted from production).

### 7.3 Edge Case Test Matrix for Field Bounds

The test suite will explicitly assert validation bounds without artificial client restrictions:

- **Customer Name**: Valid lengths: 1, 100, 101, 200 chars. Rejected: 0 chars, 201 chars, whitespace-only (`"   "`).
- **Address Text**: Valid lengths: 1, 255, 256, 2000 chars. Rejected: 0 chars, 2001 chars, whitespace-only.
- **Phone Input**: Valid VN formats (`0912345678`, `+84912345678`), valid international formats (`+14155552671`). Rejected: alphabetical characters, symbols (`abc`, `123-xyz`), lengths > 64 chars.
- **Nullable Fields**: `email` and `note` must accept `null`, `undefined`, or valid strings without throwing client runtime exceptions.
- **Unknown Fields**: Client form submissions must strip unknown properties to prevent backend `400 VALIDATION_ERROR` rejection.

## 8. Canonical API Error Contract & Mapping

### 8.1 Public Error Response Envelope (apps/api/src/http.ts)

Nexora's authoritative public error format is defined by `ApiErrorDto`:

```typescript
export class ApiErrorDto {
  code: string; // Machine-readable uppercase error token
  message: string; // User-facing localized summary
  requestId: string; // Traceable request correlation ID
}
```

_Crucial Implementation Rule_: The HTTP status code is obtained strictly from the HTTP response status (`res.status`), **never** from a nested `statusCode` property inside the JSON body. There is no `details: unknown[]` array in the production error contract.

### 8.2 Canonical Frontend Error Mapping Table

| HTTP Status | Authority Code                      | Domain Context     | Authoritative Cause                                 | Frontend Presentation & Recovery Behavior                                                                     |
| :---------- | :---------------------------------- | :----------------- | :-------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| **400**     | `VALIDATION_ERROR`                  | Global             | Malformed JSON, unknown fields, or bound violation  | Display form-level error banner. Render inline error only if field was locally validated.                     |
| **400**     | `CANNOT_CONNECT_CARRIER_ACCOUNT`    | Carrier            | Invalid provider credentials or duplicate account   | Render error on Carrier drawer: "Không thể kết nối tài khoản này. Vui lòng kiểm tra lại thông tin đăng nhập." |
| **401**     | `UNAUTHORIZED`                      | Global             | Missing, expired, or invalid session token          | Redirect to `/login?from=<safe-path>`. Zero custom session managers.                                          |
| **401**     | `PROVIDER_AUTH_FAILED`              | Carrier            | Carrier rejected credentials during reconnect       | Render error on Reconnect modal: "Xác thực với nhà cung cấp thất bại. Vui lòng kiểm tra lại mật khẩu."        |
| **403**     | `FORBIDDEN`                         | Global             | OriginGuard mismatch or insufficient role           | Display safe access denied notification: "Không có quyền thực hiện thao tác này."                             |
| **404**     | `NOT_FOUND`                         | Customer / Carrier | Resource does not exist or belongs to another owner | Treat nonexistent and inaccessible resources identically. Render customer/connection not found view.          |

### 8.3 Safe 2-Step Default Address Deletion Sequence

When a user deletes a customer address, the frontend executes the following deterministic sequence:

```mermaid
sequenceDiagram
    autonumber
    actor User
    participant UI as CustomerDetailPage
    participant API as CustomerController

    User->>UI: Clicks "Xóa địa chỉ" on Address Card
    UI->>UI: Check total addresses in Customer aggregate
    alt addresses.length === 1
        UI-->>User: Show alert: Cannot delete sole address (LAST_CUSTOMER_ADDRESS)
    else Address is NOT default (isDefault === false)
        UI->>User: Show standard confirmation dialog
        User->>UI: Confirms deletion
        UI->>API: DELETE /api/customers/:id/addresses/:addressId
        API-->>UI: 200 { success: true }
        UI->>UI: Refresh customer detail & show toast
    else Address IS default (isDefault === true)
        UI->>User: Prompt user to select replacement default address
        User->>UI: Selects new default address from existing list & confirms
        Note over UI,API: Step 1 (Request 1): Reassign default address via PUT
        UI->>API: PUT /api/customers/:id/default-address { "addressId": newDefaultId }
        alt PUT fails (e.g. 404 or 409)
            API-->>UI: Error response
            UI-->>User: Display error; abort sequence without deleting target
        else PUT succeeds
            API-->>UI: 200 AddressResponseDto (new default active)
            Note over UI,API: Step 2 (Request 2): Delete original target address via DELETE
            UI->>API: DELETE /api/customers/:id/addresses/:targetAddressId
            alt DELETE succeeds
                API-->>UI: 200 { success: true }
                UI->>UI: Refresh customer detail & show success toast
            else DELETE fails (e.g. network failure)
                API-->>UI: Error response
                UI-->>User: Partial success feedback: "Đã đổi địa chỉ mặc định nhưng chưa thể xóa địa chỉ cũ. Vui lòng thử lại thao tác xóa."
            end
        end
    end
```

### 11.4 Evidence-Based Semantic Verification Invariants

To eliminate misassigned responsibilities and ensure technical fidelity across revisions, all design specifications must satisfy the following six semantic verification invariants:

1. **Invariant A — Server-Side Authentication Ownership**:
   - The canonical workspace authorization guard lives in `apps/web/app/(workspace)/layout.tsx`.
   - The guard calls `getCachedServerSession()` and `verifyServerSession()` in `apps/web/lib/api/session.ts`.
   - Authenticated, unauthenticated, and service-unavailable outcomes are handled with distinct server actions (render, redirect, fail-closed UI).
   - `AppShell.tsx` and `ShellClient.tsx` are pure presentation components and must **never** be documented as owning an effect-based session guard.
2. **Invariant B — Frontend Implementation Existence**:
   - Every entry marked `NEXORA_EXISTING` must point to an actual source file that exists on the reviewed git baseline.
   - Backend API existence alone must **never** be treated as evidence of an implemented frontend screen.
   - Planned frontend directories (e.g., `apps/web/features/carrier-connections/`) must **never** be cited as existing source evidence.
3. **Invariant C — API Operation Ownership & Endpoint Separation**:
   - The Carrier Reconnect endpoint (`POST /api/carrier-connections/:id/reconnect`) exists in `CarrierLifecycleController`; its frontend UI is an M4 planned adaptation (`NEXORA_ADAPTATION`).
   - Customer default address reassignment (`PUT /api/customers/:id/default-address`) and address deletion (`DELETE /api/customers/:id/addresses/:addressId`) are two distinct HTTP operations with separate transactional boundaries.
4. **Invariant D — Security & Zero Secret Persistence**:
   - Demo credential Quick Fill is intentionally omitted from production `LoginForm.tsx`.
   - Plaintext passwords, MFA codes, and session tokens are never stored in `localStorage`, `sessionStorage`, or URL queries.
   - TOTP and recovery-code MFA modes are both preserved with canonical `{ type, code }` payload.
   - Upstream backend outages fail closed with informative service-unavailable UI rather than redirecting into infinite loops.
5. **Invariant E — Transaction Semantics & Non-Atomic Multi-Request Workflows**:
   - The term "atomic" is reserved exclusively for operations where the backend provides a database transaction guarantee (e.g. atomic customer creation with required initial address).
   - Multi-request HTTP workflows (such as `PUT` default-address then `DELETE` address) are sequential and non-atomic across HTTP calls.
6. **Invariant F — Documentation Integrity & Contiguous Traceability**:
   - Exact 30-file reference ZIP manifest matches the archive without omission or invention.
   - All 77 interactions have continuous IDs, valid explicit origins, and verified handler/callback strings.
   - Planned paths are explicitly labeled as planned.
