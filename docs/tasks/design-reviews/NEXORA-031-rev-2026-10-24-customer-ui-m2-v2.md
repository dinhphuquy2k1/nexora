## 7. Selected Design & Tactical DDD Alignment

### Ownership and component composition

CustomerAggregate, child address lifecycle, phone/country VOs, uniqueness, actor→parent→child locks, SQL adapters and transactions remain exclusively backend-owned. Web draft/query/view types are presentation state, not a new Domain model, aggregate, repository or source of business truth. Use SDK schema aliases and request parameter types; do not redefine response DTOs. Features import neither apps/api nor database. No transaction/concurrency policy changes.

Thin workspace route files render CustomerListPage / CustomerDetailPage from apps/web/features/customers. Next App Router useSearchParams/usePathname and Suspense are used according to installed Next16 documentation; dynamic detail params follow the current async contract. CustomerListPage composes CustomerFilters, CustomerStatsBar, CustomerTable/mobile cards, pagination and Create/Edit drawers. CustomerDetailPage composes profile, address list, Edit drawer, AddressDrawer and DeleteAddressModal. Field, payload, transport and request lifecycle concerns remain separate from rendering. No giant source-reference component port.

### URL/query and request lifecycle

Only page/pageSize/q/status/phone are Customer API query keys. Defaults page1/pageSize20; positive safe integers, page<=2147483647, pageSize<=100 and (page-1)\*pageSize<=2147483647. Reject ambiguous repeated supported keys or malformed direct-URL values with a safe invalid-filter state and explicit reset, not silent fallback to a broader population. Unknown URL keys are never forwarded to API. Trim q, omit blank/whitespace q entirely, maximum200; nonblank raw phone<=64, backend normalization only. ALL is absent status, never a persisted or transmitted code. q/status/phone/pageSize changes reset page1.

URL is the canonical committed state, including direct navigation and Back/Forward. The search input may keep a transient editing draft. Its change handler invalidates generation, aborts in-flight work and clears rows/pagination/stats/errors immediately, before the300ms timer or routing update. Next native history integrates with search-param hooks: replace the current entry for a typing burst, push explicit filter/page changes, and cancel drafts/timers on navigation. Clearing resets page1/removes q and loads unfiltered state immediately. Retry invalidates generation even for the same key. Route change/unmount invalidate and abort. Reconcile rapid input/navigation from the latest URL, not captured stale search params.

One canonical normalized key and monotonically increasing generation fence cover rows, pagination, stats, error and loading completion. AbortController is optimization, not the correctness fence. Apply success/failure/finally only when mounted and both generation/key still match. Prevent the interval between a UI/query change and effect cleanup from accepting stale A into B. Response runtime guards reject malformed row/detail/pagination/status envelopes safely. No stale results are displayed as current.

Stats uses response.stats only. Require safe non-negative integers and total=active+inactive. q/phone determine stats population; status/page/pageSize do not filter stats. Distinguish initial/loading, successful empty0/0/0, valid populated result, request error and unavailable/missing/malformed stats. An old server with otherwise valid rows can show those rows plus unavailable stats; it cannot manufacture0. No per-row detail fetch or addressCount inference.

### Forms and payloads

Use explicit typed allowlist builders, never spread responses/drafts. name/recipientName trimmed1..200; raw phone/recipientPhone1..64 without a custom normalization algorithm; email1..254 nullable; note1..5000 nullable; label1..100 nullable; addressText1..2000; countryCode two-letter input per current API with backend ISO authority. Frontend length/required/type UX checks do not claim backend-equivalent phone/email/ISO validation. Use native email UX and safe400 handling rather than importing backend validators.

Create requires name/phone and initial addressText; optional blank email/note/label are omitted. Blank optional recipient fields are omitted so backend applies fallback; explicit supplied recipients may differ. Send countryCode VN by default, no code/status/owner/creator/isDefault. Backend atomically selects the first default. Edit only submits changed allowlisted profile/status values; blank nullable values clear with null, required blanks are UX errors; unchanged/empty PATCH does not submit. Editing profile never rewrites recipient addresses.

AddressForm has initial/add/edit modes and keeps countryCode/addressText names aligned to SDK rather than reference country/addressLine. Add can omit recipient fields for backend fallback; edit preserves existing recipients and only changes dirty fields, nullable label clearing via null. Generated AddressPatchDto currently marks countryCode required because of the OpenAPI default; include the existing or explicitly edited countryCode when another field changes, without replacing generated DTOs or changing API. No-op edit remains blocked. Never send isDefault, identity or parent reassignment. Explicit default action sends only {addressId} to PUT.

Mutations use one parent-scoped in-flight guard, disable duplicate submission and prevent overlay dismissal while pending. Failures preserve form content and errors; only confirmed success closes/resets. Refetch/invalidate after committed success and409 conflicts; a success message denotes the committed mutation, not successful refresh. A refresh failure shows saved-but-refresh-unavailable/retry. Do not retry POST/PATCH automatically on network ambiguity; reconcile with server before retrying. List refresh uses current query and detail refresh current id, with generation fencing. Unmount suppresses stale completion/navigation but does not claim to cancel a server commit.

### Address deletion and legacy state

Block last-address deletion with explanation and Add Address path. Ordinary deletion requires confirmation. Default-with-alternatives requires an explicit selected replacement from current addresses, then PUT default and, only after successful acknowledgment, DELETE target. PUT failure means no DELETE. DELETE failure after successful PUT is partial success: retain new default, show safe message, refetch, keep target for explicit retry after reconciliation; no reverse PUT rollback or atomicity claim. If DELETE response is ambiguous, refetch first; already-absent target is not blindly deleted again. Concurrent404/409 refreshes owned detail and explains changed state. Replacement removed/default changed concurrently remains backend-authoritative.

Historical zero-address/no-default views show actual data. Add Address and Set Default are explicit owner actions; no recipient/default fabrication or repair on read. Detail count is actual addresses.length only. INACTIVE records remain readable/editable; no new Shipment policy.

### Errors, accessibility and visual direction

One feature-local error classifier keeps HTTP status and safe code/message behavior together.400 uses safe general validation feedback, no invented server field details;409 CUSTOMER_PHONE_EXISTS links feedback to phone;409 last/default codes preserve deletion flow;404 foreign/nonexistent identical.401 redirects through existing sanitizeReturnUrl to /login?from;403 is forbidden/Origin, never session expiry. Network/500/malformed data have safe retry; do not render untrusted server text or log PII/body/session data. Preserve requestId only when safely validated; do not replace backend ErrorFilter/envelope.

Use M1 semantic tokens, CSS Modules and shared controls. No !important, raw color/control-style duplication or blanket CSS scanner exceptions. Native Select shares height/radius/font/border/focus/disabled/invalid contract; use disabled for pending, not invented select readonly semantics. Label suggestions are actual feature actions, not a new shared chip library. Sidebar/header dimensions and all existing M1 controls remain compatible.

Desktop uses reference hierarchy and a semantic table with code/name/phone/email/status/date/actions; mobile uses cards or a contained table scroller with reachable actions, never body horizontal overflow. Detail profile/addresses stack on small screens. Drawers fit viewport width/height with internal vertical scrolling; initial focus and aria-labelledby/describedby/invalid/busy/status feedback, Tab/Shift+Tab, Escape/backdrop and return focus are mandatory. Restore focus to live trigger or stable page heading if mutation/navigation removed it. No nested feature dialogs. Available Customer menu is activated only after route acceptance and independent nav contract tests change together; other planned items remain untouched.
