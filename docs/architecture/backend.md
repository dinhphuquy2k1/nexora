# Backend

`HealthController` maps HTTP to `HealthService`; the application service consumes database/storage health ports. DatabaseAdapter is infrastructure and lazily constructs Prisma so liveness remains available when database operations fail. DB URLs use a 3-second connect timeout in Compose. No AI dependency is required for readiness.
`FilesService` writes the original blob then registers hash/size in the catalog; catalog failure removes the new blob. This is an internal service, with no public upload endpoint. Process crashes between filesystem and catalog writes may leave an orphan; recovery/retention belongs to the ingest milestone. Successful stored files are immutable through the current service.
Config validates required DB URL, canonical absolute storage root, port, node environment and explicit Swagger toggle. Errors expose safe code/message/requestId. JSON HTTP logs contain requestId, status and duration only; headers, query strings, request bodies, cookies, credentials, file contents and notes are excluded by construction. Express trust proxy is configured strictly for trusted internal network hops (loopback, linklocal, uniquelocal); arbitrary forwarded headers from external clients are not trusted. CORS is not enabled.
`AuthController` handles local session lifecycle (`/api/auth/login`, `/api/auth/session`, `/api/auth/logout`) delegating to `AuthService`. Sessions use 32-byte opaque random tokens hashed with SHA-256 in PostgreSQL and transported via `nexora_session` HTTP-only cookies. Login validates body field types before normalization, admission or database work. Username identity is case-sensitive and trimmed consistently with provisioning; valid usernames contain 3–50 characters and Login passwords 1–1024 characters (provisioning requires 8–1024). Invalid fields return 400 VALIDATION_ERROR. Protected business routes enforce global `SessionGuard` registered via `APP_GUARD`, returning 401 UNAUTHORIZED without leaking database internals. Infrastructure health endpoints (`/api/health/live`, `/api/health/ready`) and public auth endpoints (`/api/auth/login`, `/api/auth/logout`) are exempted via `@Public()`. Browser mutations (`/api/auth/login`, `/api/auth/logout`) enforce exact configured Origin through `OriginGuard`; see [configuration](../operations/configuration.md). Missing Origin is forbidden even for internal callers. Expired-session cleanup is executed with isolated error handling to prevent unhandled Promise rejections. Explicit logout uses idempotent `deleteMany`; database failures propagate as safe 500 errors and never produce success or a clearing cookie.

Authentication admission owns bounded process-local state: at most 128 case-sensitive account entries, five failed attempts within a five-minute window, and success clears that account counter. Pending attempts reserve counter capacity synchronously. Before lookup or Scrypt, a global token bucket admits a burst of 10 attempts, refilling one token per second, with at most four concurrent admissions. This permits normal small-instance operator retries while limiting Scrypt CPU and memory during username rotation; rejected requests do not query or hash. Remove expired non-pending entries first, then evict the oldest unlocked/non-pending entry; active locks remain until expiry. If every entry is locked or pending, new accounts receive 429. This intentionally permits temporary denial of new logins under saturation instead of erasing active lockouts. An existing unlocked account may still log in, subject to the global budget. In canonical Docker, client IP may be the proxy/gateway; account keys and the global budget do not assume distinct operator IPs.

Unknown and inactive identities use one precomputed dummy hash generated by the existing `hashPassword` implementation; real Scrypt verification runs before returning the same 401 as wrong credentials. No dummy account exists, and no verification occurs after admission rejection. The compiled trusted CLI (`dist/cli/user-create.js`) delegates provisioning to `identity/infrastructure/user-provisioner.ts`, preserving database ownership and the shared hashing implementation.

## Local identity and transaction boundaries

`AuthService` verifies the existing Scrypt hash outside the transaction. `IdentityDatabaseAdapter.createSessionIfUnchanged` then locks the user (`FOR UPDATE`), checks ACTIVE status, ADMIN/OPERATOR role and the exact verified credential hash, and inserts the opaque session atomically. Changed credentials or concurrent disablement prevent issuance. SessionGuard rechecks current database status; AdminGuard additionally reads current database role/status and session auth_level; ADMIN + MFA are required, never body/header/frontend claims.

`UserManagementService` owns operator creation, setup-link reissue, password setup and approved user status/list contracts. `UserManagementAdapter` owns Prisma transactions. Every consume/reissue/disable locks users before token writes. Actor and target rows are locked in ascending UUID order. Scrypt stays outside consume transactions. Conditional consumption uses `clock_timestamp()` so a token that expires while waiting for a lock cannot succeed. Credentials cannot be overwritten.

Status transactions acquire the shared transaction advisory lock before user rows, preserving at least one ACTIVE ADMIN. Disable atomically updates status, deletes sessions and invalidates pending setup tokens. Reactivation restores neither. Administrative writes recheck the actor under lock. Summaries contain only approved fields, with `hasPassword` rather than hashes.

Login and setup share the existing process-wide admission budget (burst 10, refill 1/sec, concurrency 4) and bounded account/token-hash counters. Existing `FORBIDDEN` Origin and `TOO_MANY_REQUESTS` limiter error codes are retained; login credential failure is `AUTHENTICATION_FAILED`.

## Independent Uniship transport

Legacy provider login and Identity provider ports/types are removed. The retained client lives in `carrier/infrastructure/uniship/uniship-http.client.ts`, with independent `externalAccountId` output. It preserves HTTPS, timeout, redirect rejection, bounded payload, nested user/token/`userid` validation; `is_verified` is ignored under the dated PR4 owner amendment and safe error mapping. Carrier safety tests use local mocks only. No client is wired to Nexora authentication or sessions, and no live Uniship call is made.

## Multi-Carrier Modular Architecture (Target Architecture — ADR-007)

Under [ADR-007](../decisions/multi-carrier-architecture.md), the backend modular monolith separates operator identity from external logistics provider management:

1. **Module Organization**:
   - `apps/api/src/identity/`: Owns local Nexora operator identity (`users`, `user_credentials`, `sessions`, `operator_setup_tokens`; `user_mfa`, `mfa_challenges` and `mfa_recovery_codes` are introduced by PR6). In PR 2, `POST /api/auth/provider/login`, `AuthService.loginWithProvider()`, and `authenticateExternalIdentity()` are completely eliminated. The implemented module uses `UserManagementService` for single-use onboarding links (`POST /api/admin/operators`, `POST /api/admin/operators/:id/setup-link`, and `POST /api/auth/setup-password`).
   - `apps/api/src/carrier/`: Owns multi-carrier connections (`carrier_connections`), encrypted credential persistence (`carrier_connection_secrets`), connection lifecycle, and carrier adapters. Uniship HTTP client is refactored into `carrier/infrastructure/uniship/`.
   - `apps/api/src/common/crypto/`: Central cryptographic module implementing AES-256-GCM, HKDF subkey derivation, 96-bit CSPRNG nonces, and authenticated associated data (AAD) binding. Both Identity and Carrier consume this module; neither module imports cryptographic routines or domain entities from the other.

2. **RBAC, Concurrency Invariants & Multi-Level Session Assurance**:
   - `SessionGuard` validates the active opaque session globally as `APP_GUARD`.
   - `POST /api/auth/mfa/verify` is explicitly decorated with `@Public()` to bypass `SessionGuard` during the two-step login sequence, but is strictly protected by `OriginGuard`, pending challenge cookie validation (`SameSite: Strict`, `HttpOnly`), account-level rate limits, and atomic replay protection.
   - **Password-Hash Recheck in Session/Challenge Issuance**: Scrypt password verification runs outside the database transaction. Subsequently, inside a short transaction, the server locks the user row (`SELECT ... FROM users ... FOR UPDATE`), verifies `status = 'ACTIVE'` and the expected role, and strictly re-verifies that `user_credentials.password_hash` exactly matches the hash used for the Scrypt verification. Any mismatch indicates a concurrent password change and immediately aborts issuance.
   - **Last Active Admin Invariant & Advisory Lock Protocol**: To prevent deadlocks from inconsistent lock ordering and eliminate race conditions that leave zero active administrators, operations reducing active administrators (disablement, demotion, self-disablement) acquire a dedicated transaction-level PostgreSQL advisory lock (`SELECT pg_advisory_xact_lock(hashtext('nexora_active_admin_invariant'))`) before any row-level locks. The transaction-level advisory lock acquired before user-row locks serializes administrative operations that reduce active administrators adhering to this protocol, preventing lock-ordering deadlocks and race conditions specifically between those administrative mutations while strictly guaranteeing that the active administrator count never falls to zero. Transactions holding advisory locks are never held across HTTP calls or slow I/O.
   - **CLI TOTP Enrollment Protocol (No Locks During Prompt)**: The interactive CLI (`dist/cli/mfa-enroll.js`) executes password verification, secret/recovery-code generation, and confirmation TOTP verification strictly outside database transactions. After confirmation code verification, a short transaction locks the user row (`SELECT ... FOR UPDATE`), re-checks role, status, and password hash equality, commits `user_mfa` (with `last_used_step`) and recovery code hashes, and atomically invalidates active sessions and challenges. Recovery codes are displayed once only after transaction commit.
   - **Operator Setup Link Protocol & Reissue**: `POST /api/admin/operators` generates a high-entropy CSPRNG token (≥128 bits entropy), stores only its SHA-256 hash in `operator_setup_tokens` (24h TTL, single-use), and returns the setup URL once. `POST /api/admin/operators/:id/setup-link` allows ADMIN to reissue an onboarding link for an ACTIVE OPERATOR who has no credentials, locking the user row first and atomically marking all previous unconsumed tokens for that user as consumed. `POST /api/auth/setup-password` (`@Public()`, `OriginGuard`) strictly follows the unified lock order (**user row lock → operator_setup_tokens update**): Scrypt hashing executes outside the transaction, a non-locking lookup locates `user_id`, a short transaction locks user row FIRST (`SELECT ... FOR UPDATE`), verifies `ACTIVE` OPERATOR, conditionally updates setup token, verifies absence of `user_credentials`, and inserts the Scrypt hash. If credentials exist, it fails with `400 OPERATOR_ALREADY_CONFIGURED`. All setup token operations adhere to this lock order, eliminating deadlocks. Disabling an OPERATOR atomically invalidates all unconsumed setup tokens in the same transaction; reactivation does not restore them. Plaintext tokens are never logged or stored.
   - Route-level RBAC decorators enforce specific roles and authentication levels:
     - Standard operator routes: Require active user session (`auth_level = 'PASSWORD'` or `'MFA'`).
     - Administrative endpoints (`/api/admin/...`):
       - **PR 2 → prior to PR 6**: The database schema in PR 2..5 does NOT contain a `sessions.auth_level` column. Local `ADMIN` users with valid password sessions can access administrative onboarding endpoints (`POST /api/admin/operators`, `POST /api/admin/operators/:id/setup-link`). The backend strictly validates `role === 'ADMIN'` and active session. In this milestone, "PASSWORD" is a logical assurance property, NOT a database field. This interim policy is supported exclusively on local loopback environments; administrative endpoints and login are never exposed to the public Internet without MFA. Does not depend on unreleased MFA components.
       - **From PR 6 onward**: Every administrative endpoint strictly requires `role === 'ADMIN'` AND `auth_level === 'MFA'`. Password-only admin sessions are revoked or rejected. No permanent MFA bypass is retained.
       - **PR 7**: The public HTTPS profile verifies during boot that MFA enforcement is strictly enabled; any attempt to run public administrative endpoints without MFA fails closed.
     - Carrier connection operations (`/api/carrier-connections/...`): Strictly enforce connection ownership (`user_id` matching session). Administrative sessions cannot decrypt, reconnect, or trigger carrier API operations on behalf of another user.

3. **Carrier Connection Orchestration**:
   - **Connection Lifecycle**: Supports `CONNECTED`, `REAUTH_REQUIRED`, and `ERROR` states.
   - **Unified Generic Error Mapping**: `POST /api/carrier-connections` returns a single unified generic error (`400 CANNOT_CONNECT_CARRIER_ACCOUNT`, "Không thể kết nối tài khoản này") for both invalid provider credentials and duplicate account linkage (`UNIQUE(provider, external_account_id)`). This eliminates account enumeration hazards while the underlying event (`PROVIDER_AUTH_FAILED` vs `DUPLICATE_EXTERNAL_ACCOUNT`) is logged to the safe server-side security audit sink.
   - **Protected Carrier Endpoints**: All protected carrier endpoints enforce `401 UNAUTHORIZED` if the caller's session is missing or expired.
   - **Deferred Administrative Carrier Endpoints & CLI**: Administrative carrier endpoints (`GET /api/admin/carrier-connections`, `DELETE /api/admin/carrier-connections/:id`) require `ADMIN + MFA` and are deferred to post-PR 6. The interim Carrier Admin CLI (`dist/cli/carrier-admin.js`) is also **PLANNED / DEFERRED** post-PR 6 and is not supported in PR 2..5; interim cross-user maintenance during development is conducted exclusively via authorized direct SQL maintenance runbooks by database administrators.
   - **Token Verification (`api-token-verify`) & Merge Gate**: Candidate access tokens must be verified against `POST /client/api-token-verify/` after login ensuring `user.userid == external_account_id`. Identity mismatch marks connection `REAUTH_REQUIRED` and prevents automatic re-login until successful manual reconnect. PR 4 development uses a mock adapter until live merge gate requirements (request body, identity proof, TTL, refresh rules, quotas, and re-login authorization) are verified through formal API evidence.
   - **Durable Audit & Fail-Closed Decryption**: Decrypting saved passwords for automated re-login requires persisting an immutable security audit event through `SecurityAuditPort`. If the audit sink fails or is unavailable, decryption is immediately aborted (fail-closed).
   - **Singleflight Concurrency**: In-memory singleflight per `connection_id` prevents redundant token refresh or re-login storms within a single API instance. Database transactions are never held across external HTTP calls.
   - **Carrier Budget & Backoff**: Outbound requests are governed by per-carrier concurrency budgets; HTTP 429 triggers carrier-wide backoff without spamming logins.

## Legacy session upgrade boundary

The owner-approved cutover in [ADR-007](../decisions/multi-carrier-architecture.md) is implemented by a new migration. Every OPERATOR session without a local credential is deleted at upgrade, including expired/DISABLED-user sessions. ADMIN and configured OPERATOR sessions are retained. SessionGuard is unchanged; removed tokens cannot regain validity after setup. No auth-source metadata exists to distinguish sessions of configured operators.

## Implemented Logical PR 3 Carrier foundation — NEXORA-017

CarrierController delegates metadata GET/PATCH/DELETE to CarrierService and CarrierPort; CarrierAdapter alone owns database access. Global SessionGuard authenticates, OriginGuard protects mutations, and owner predicates apply equally to ADMIN and OPERATOR. Explicit select lists exclude owner IDs and all secrets from connection DTOs. No create/reconnect or administrative Carrier routes are registered.

SecretCipher in common/crypto implements AES-256-GCM, fresh 12-byte random nonces, separate 16-byte tags, canonical base64 and HKDF-SHA256 subkeys. HKDF salt is the protocol domain NEXORA_CARRIER_V1 and info is CARRIER_TOKEN or CARRIER_PASSWORD. CarrierSecretWriter constructs exact AAD connection_id:user_id:provider:secret_type, encrypts outside the transaction and locks ACTIVE owner before connection verification and encrypted upsert. The writer has no read/decrypt method and no HTTP exposure. Generic primitive decrypt is unit-tested; PR4 adds the audited credential vault below; the generic writer still cannot decrypt.

EnvironmentKeyring snapshots server configuration but validates lazily at crypto use, keeping missing/malformed Carrier keys isolated from local Login, ADMIN operations and metadata. Errors expose only SECRET_CRYPTO_UNAVAILABLE, never underlying key/plaintext. Ciphertext/key failure changes neither persisted ciphertext nor connection status. Version rotation is configuration-only; no key removal or automated re-encryption path exists.

## PR4 backend lifecycle implementation — NEXORA-018

Uniship transport now supports candidate token verification and bounded response reads, ignores `is_verified`/username for acceptance and remains hard-closed to external requests pending official provider authorization. A provider adapter requires login/verify userid coherence; expiry parsing supplies nullable scheduling metadata only. Nexora-side admission defaults are five attempts/user/minute (1024 tracked identities), two concurrent provider acquisitions (at most two HTTP calls in flight) and capped temporary-failure backoff honoring valid Retry-After. These are local safety choices, not verified Uniship quotas.

Pure Carrier lifecycle orchestration and credential ports implement: per-connection typed-outcome singleflight (NEXORA-021 clarification below), one recovery at most per operation, no refresh endpoint or global plaintext cache, mismatch/manual-reauth suppression and version-based stale-result handling. The infrastructure vault requires a durable audit append before password decrypt and rechecks authorization afterward. The owner approved PostgreSQL SecurityAuditPort storage on 2026-10-16: security_audit_events has typed allowlisted metadata only and append-only mutation triggers. Password-decrypt audit commits independently before decrypt; success audit participates in atomic connection/secrets transactions. Failure audit distinguishes duplicate credentials without public ownership leakage. AppModule wires the lifecycle and two POST routes; no Web changes, workers, refresh or cross-user APIs. External transport remains hard-closed. Verification evidence and exact-head CI are recorded in NEXORA-018.

The lifecycle adapter locks ACTIVE user then its Carrier epoch/connection in short transactions; creates commit verified metadata plus sealed password/token atomically. Each claim increments connection lifecycle_version; completion/failure compares version and user generation before writing, completion increments again. Disable increments generation even for a user without connections, increments all connection versions, deletes secrets and sets REAUTH_REQUIRED in the existing revocation transaction. Reactivation restores nothing. Metadata rename does not invalidate credential work. CarrierSecretWriter also checks/increments version and refuses REAUTH_REQUIRED. No DB transaction spans HTTP, password decrypt or encryption. Typed recovery flight state is bounded 128 and removed in finally; it never caches plaintext.

## Manual replacement vs automatic recovery — NEXORA-020

CarrierConnectionLifecycleService has separate handleReconnectFailure and handleRecoveryFailure policies. A failed new credential candidate preserves the prior connection status, complete encrypted secret rows, lastVerifiedAt and identity/ownership. Only verified userid differing from stored externalAccountId invokes the existing fenced REAUTH_REQUIRED write. Success still atomically commits encrypted password/token and CONNECTED plus success audit. Normal manual failures do not write status; claim's version/updatedAt may advance for fencing, independently of credential replacement. No stored password is decrypted for a manual attempt. Existing failure audit is still required.

UnishipAdapter classifies contradictory login/verify identities as CANDIDATE_IDENTITY_MISMATCH, distinct from the service/adapter's verified stored IDENTITY_MISMATCH. Both map to unchanged public errors and existing audit reason. Recovery keeps its original status classification, including candidate inconsistency requiring reauth; temporary provider errors/429 remain ERROR with backoff and crypto failures leave state untouched. Audit-before-decrypt, ACTIVE-user generation/version CAS, singleflight and retry budgets are unchanged. Real PostgreSQL/Nest tests exercise actual nexora_app credentials and late verified mismatch after newer manual success; schema, roles, audit sink, crypto and live authorization are untouched.

## Superseded lazy recovery — NEXORA-021, 2026-10-16

Lifecycle version/generation remain authorization and write fences, not evidence of committed credentials. Recovery now returns a small private COMMITTED/SUPERSEDED/JOINED outcome with an attempt flag, replacing the historical Promise<void> flight result. Every outcome requires a fresh owner-scoped read and status/token/expiry/rejection check before token use. A failed manual claim can leave the same expired or rejected token; only an eligible changed sealed token can be reused without another login. Unknown expiry is never a validity guarantee.

LifecycleSnapshot adds internal tokenRevision, computed after the database transaction from SHA256 of stored token ciphertext, nonce, tag and key version. Existing timestamps have millisecond resolution and row IDs survive upsert, so neither reliably proves rotation. The digest never uses plaintext or keys and never reaches DTOs, logs or audit. No schema column, encrypted format or keyring change. The application treats it as opaque metadata; encryption/decrypt/provider I/O remain infrastructure-only.

Each logical withToken operation shares at most3 recovery-flight decisions across initial expiry and rejection handling, at most1 vault/password recovery attempt and at most1 provider-operation retry. Version-only supersession and claim CAS loss before vault entry consume rechecks but no password attempt. A joined flight shares its leader's attempt consumption. Vault entry conservatively consumes the only attempt even if a later STALE occurred before decrypt, since it might instead have occurred after provider acquisition. Repeated churn or an unusable result with no budget returns existing STALE (safe503), never false recovery success or an unbounded login loop. Flight metadata remains bounded128, contains no plaintext and is cleaned on success/failure.

A stale recovery completion may reuse a newer manual winner only after current authorization and token evidence pass; it cannot overwrite that winner. Disable/delete/REAUTH_REQUIRED remain fail-closed. Existing user-first locks, generation/version CAS, durable audit-before-decrypt/revalidation, manual replacement policy, recovery failure classification, provider budgets/backoff and live gate are unchanged.

Observed-expired token revisions remain unusable across recovery rechecks even if expiry metadata later becomes null or future-dated without changing the sealed artifact. NEXORA-021 pins this evidence alongside known provider rejection; metadata alone cannot establish replacement. A deterministic unit regression and the genuine PostgreSQL single-caller barrier cover the null-expiry supersession case.

## Mandatory ADMIN MFA — NEXORA-022 (2026-10-16)

AuthService preserves Scrypt outside locks and independent local OPERATOR PASSWORD sessions. ADMIN password verification creates only a five-minute hashed challenge after an ACTIVE ADMIN/hash recheck under user lock; no intermediate authenticated session. Correct-password unenrolled administrators get403 MFA_ENROLLMENT_REQUIRED with trusted CLI guidance. Up to five pending challenges per account are retained; consumed/expired/older excess rows are removed under the same user lock. Password failures remain anti-enumerating.

IdentityMfaAdapter decrypts/HMAC-verifies outside transactions, then user-locks before checking exact sealed enrollment evidence, database clock expiry/window, challenge single use, monotonic last_used_step or owned recovery-code consumption and MFA session insertion. A later failure rolls back all three writes. Distinct challenge/recovery races serialize on user; no input, HTTP or Scrypt is held under locks. Enrollment initializes last_used_step to the confirmation step. New enrollment is never an upsert/reset. Disable adds challenge revocation to the existing advisory-before-sorted-users/Carrier epoch and secret revocation transaction; reactivation restores nothing.

MfaService uses AuthService's bounded global admission and a separate mfa:userId counter: password successes/new challenges cannot clear MFA failures. Five failed/pending attempts per five minutes,128 tracked keys,global burst10/refill1s/concurrency4 remain per-instance safeguards. Invalid challenge tokens never invoke TOTP crypto. Recovery codes are an explicitly approved factor, not a crypto-error fallback: valid single-use recovery verification does not decrypt the TOTP secret; missing Identity keys fail TOTP/enrollment closed.

Global SessionGuard and AdminBoundaryGuard protect all administrative namespaces using registered Nest path metadata plus the actual routed /api/admin path, covering future/dynamic controllers and preventing Public bypass. AdminGuard re-reads active role and the database session assurance/expiry; client assurance is ignored. Public user payloads stay id/username only. No MFA/enrollment toggle or administrative password bypass exists. Normal workspace accepts any valid ACTIVE session; preserved legacy PASSWORD ADMIN rows cannot access admin APIs.

Admission keys are explicitly namespaced as login:<username>, mfa:<user UUID> and setup:<token hash>. A valid username resembling an MFA key cannot collide with or clear another account's verification failures. NEXORA-022 test-first regression reproduces the collision and verifies the sixth bad MFA attempt remains429 after a successful password login with such a username.

The pure shared deployment policy has real Web/API consumers; strict exact authorities/origins and canonical URL semantics are shared without secrets or DB imports. API additionally validates explicit proxy CIDRs; no blanket public trust. Cookie policy centralizes every session/pending set and clear, selecting Secure from profile only. No writes, session upgrades or cleanup occur in this gate. Unknown guard registry shape/database/key failure prevents startup. No migrations, Carrier crypto/protocol/live activation or public enrollment/reset route.

## Customer Backend V1 — NEXORA-027

`customer/domain` owns CustomerStatus, bounded strict validation and normalized phones; `application` owns the small actor-only owner resolver, port and service; `infrastructure/CustomerAdapter` alone consumes Prisma; `presentation/CustomerController` delegates eight endpoints. AppModule registers the controller and explicit service/adapter factories. Customer is independent of Identity/Carrier application services except existing global SessionGuard and mutation OriginGuard; no admin route, extra permission framework or login/MFA/session change.

All adapter transactions lock the actor user first and reject non-ACTIVE status after waiting. Mutations then lock a customer by both id and owner. Final queries remain owner-scoped; address writes constrain addressId, customerId and the related customer's owner. Reads also hold the actor lock, serializing with application writes for consistent list count/page. There is no external I/O under locks. The small-instance owner lock intentionally serializes writes for the same user; no new queue/advisory-lock framework is introduced. Default changes lock the parent and preserve partial uniqueness; initial customer/address failure rolls back both. Prisma owner-phone unique violations map narrowly to CUSTOMER_PHONE_EXISTS; unrelated database errors retain existing safe500. HTTP logging/error filter remain unchanged and exclude PII by construction. See [Customer domain](../domains/customers.md) and [API](api-contract.md). Customer frontend/Shipment remain PLANNED; runtime evidence is independent of implementation status.
