# Deployment scope

IMPLEMENTED target: local, single machine, loopback web exposure only. No login/session/RBAC, public TLS, remote access policy, managed key storage, scaling, rollout/rollback or public production topology has been selected. Do not expose this foundation on the Internet.
Distribution template pins application tags 0.1.0, but those images are NOT PUBLISHED; `--prebuilt` cannot be promised to users. Task only builds local images. Registry publication, signed release/digests and a verified Windows/macOS distribution are future explicit release tasks.
Local database uses persistent generated credentials, not shared committed passwords. Volume snapshot/backup is separate from image build. Restart must not rotate credentials or remove data. CI runtime smoke is evidence for local release semantics, not proof of production hosting readiness.

## Public HTTPS Deployment & MFA Release Gates (PR 7)

Under [ADR-007](../decisions/multi-carrier-architecture.md), public deployment of Nexora is planned for PR 7 subject to the following gates:

1. **Mandatory PR 6 Prerequisite**:
   - Every ADMIN account must have completed TOTP enrollment via `pnpm mfa:enroll` prior to public exposure.
   - The application runtime enforces this at boot: if public profile is enabled and MFA enforcement is disabled, the API process refuses to start.
2. **TLS Ingress & Network Hardening**:
   - Public TLS termination must provide modern cipher suites and HTTP/2 or HTTP/3.
   - Host Header and CORS/Origin allowlists must be strictly configured in server configuration.
   - Ingress reverse proxy must pass client IP only through trusted proxy subnet configuration (`trust proxy`).
3. **Host Clock NTP Synchronization**:
   - Because Docker containers inherit the host kernel clock and TOTP requires time accuracy within ±30 seconds, the host must run an active NTP daemon (`chrony` or `systemd-timesyncd`).
   - Runbook verification command on the Linux host:
     ```bash
     timedatectl status
     ```
     Deployment requires `NTP service: active` and `System clock synchronized: yes`.
4. **Remote Operator Onboarding**:
   - Remote operators receive a single-use, cryptographically secure onboarding setup link generated by an administrator.
   - The setup link is valid for a short duration (e.g. 24 hours), consumed atomically, and allows the operator to set their initial password directly over HTTPS without the administrator ever seeing or handling their credentials.
