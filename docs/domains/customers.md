# Customer Management Backend V1

Verification and remaining gates are tracked in [NEXORA-027](../tasks/active/NEXORA-027-customer-management-backend.md); implementation is not a claim that mandatory runtime checks passed. ## Ownership and identity

A Customer belongs directly to one existing Nexora user. `resolveCustomerOwner(actor)` currently returns only the authenticated actor.id. Creation sets owner and creator to that actor in the infrastructure transaction. Neither field nor customer code/status is accepted at creation. ADMIN has no cross-owner Customer access; both roles manage their own records. Customer identity is not an application login, user account or Carrier connection. Carrier ownership/authorization is unchanged.

Two independent owners may store the same phone. Within one owner, the E.164-normalized phone is unique even when one input is0912345678 and another is+84912345678. Name/email are not unique. Code is globally unique, sequence-generated KH000001 with minimum-six digits, grows beyond KH999999 and permits rollback gaps; it is never a per-owner counter or client input. No Customer DELETE API exists; INACTIVE preserves the record/addresses and remains readable/editable. Future Shipment rules for INACTIVE customers are undecided.

## Validation

Phone parsing uses pinned libphonenumber-js1.13.15/max, VN for national inputs, explicit international numbers supported; invalid numbers/extensions rejected and recipients normalized independently. Postal country is independent of the phone's national default. ISO3166-1 alpha-2 is validated with pinned i18n-iso-countries7.14.0, excluding its non-ISO XK extension; trim/uppercase, default VN. No geopolitical/province/ward model is introduced.

Trimmed lengths: name/recipientName1..200, label1..100, addressText1..2000, email1..254, note1..5000; raw phone input1..64 before parsing, persisted E.164 at most16. Email uses the existing Zod email validator. Nullable email/note and address label accept null (including PATCH clearing); null/blank required fields, extensions, invalid status/UUID and unknown/mass-assignment fields reject400. Empty PATCH rejects400. CustomerStatus ACTIVE/INACTIVE codes are owned by @nexora/shared with a database CHECK; Customer Domain owns CustomerStatusVO; no enums.

## Recipient addresses

Every valid Customer created through Customer API V1 must have at least one recipient address and exactly one default address. Creation requires a non-null, nonempty address with addressText; missing/null/array/blank addresses reject400 before persistence. Omitted recipient values use normalized customer values, country defaults VN and the initial address is always default. Customer and address commit atomically. Later customer edits do not rewrite independent recipient values. There is no address-count limit.

Deletion verifies scoped parent/child existence first404, then rejects the last address with409 LAST_CUSTOMER_ADDRESS, then rejects a default with alternatives with409 DEFAULT_ADDRESS_REASSIGN_REQUIRED. The owner must select another default before deleting the previous one. All checks/count/delete occur in the same parent-locked transaction. No automatic promotion or silent removal of a default occurs.
Address PATCH cannot reassign customer or change isDefault. Dedicated default selection verifies the parent and address under one parent-row lock, clears/sets atomically and is idempotent if already selected. Every mutation first locks/rechecks ACTIVE actor, then owner-scoped customer, then addresses. Concurrent additions/default/deletion serialize on that parent; a partial unique index enforces only at most one default; application creation/deletion/selection rules preserve at least one for valid API records. Initial customer/address creation is one transaction. Owner/creator FKs RESTRICT user deletion; address FK cascades only if a Customer is deleted by authorized database maintenance in a future policy. No maintenance/delete API is introduced here.

For endpoint/pagination/error details see [API contract](../architecture/api-contract.md); physical sequence/grants/constraints belong to [Database](../architecture/database.md). No Customer PII is added to logs.

Historical zero-address/no-default data is not automatically fabricated, deleted or arbitrarily assigned a default. Physical schema does not enforce cross-row minimum cardinality. Reads do not silently repair invalid stored cardinality; the owner supplies real data through Add Address or explicitly chooses an owned address through Set Default. Never invent recipient data or select a default arbitrarily. Customer Operator Data Audit is not required for NEXORA-027 merge and no operator dataset is certified. List addressCount remains deferred. NEXORA-030 implements list stats as described below; no counts may be inferred by summing a page.

## Tactical DDD reference model

CustomerAggregate is the root; CustomerAddressEntity is a child with stable persisted identity and no independent repository/lifecycle. create/rehydrate/updateProfile/addAddress/updateAddress/removeAddress/setDefaultAddress implement the transitions above. Creation drafts require a first/default address; pending child ID and root identity are null until database insertion, never invented domain counters/UUIDs. Technical E.164 phone normalization and ISO 3166-1 alpha-2 country validation are owned by neutral common Value Objects in `apps/api/src/common/value-objects/` ([ADR-009](../decisions/mandatory-pre-code-design-review.md)). Customer domain policy retains its specific business invariants: maximum raw input length of 64, default national country context `"VN"` for phone parsing, recipient phone fallback, per-owner phone uniqueness, default recipient country `"VN"` for addresses, and translation of validation errors to domain-local `CustomerError("VALIDATION_ERROR")`. CustomerStatusVO owns status validation/initial value/equality; CustomerError stays domain-local, while codes are canonical shared vocabulary.

Root identity (id/code/owner/creator/timestamps), profile and addresses are private; returned snapshots/operation data are copies, including dates. Caller edits cannot mutate aggregate state/default flags. Entity updates validate recipient fields; root owns membership/default/minimum cardinality. Domain policies are reused by input preparation and transitions so no alternate phone/country/status algorithms exist. Application strict allowlists, empty PATCH/UUID and pagination parsing stay outside domain. CustomerService/CustomerPort orchestrate use cases and exhaustive error mapping without Prisma.

Infrastructure owns ACTIVE actor→owner-scoped Customer locks, hydrates consistent state inside that transaction through customer.mapper.ts, invokes the aggregate and persists minimal scoped changes. Default SQL clear/set order preserves the existing partial unique index. Database still owns code/UUID/timestamps and uniqueness under races; domain never replaces locking. GET projections do not hydrate full aggregates. No new DB schema/runtime grants are introduced; the later owner-approved statusLabel addition below amends API/SDK response shape.

rehydrate preserves legacy zero/no-default cardinality and other stored values as-is while validating the persisted status code; it does not impose new-creation validation on historical data, fabricate data or silently repair on read/profile edit. Owner Add Address and explicit Set Default retain their existing recovery semantics. Invalid new creation is rejected; ordinary API operations do not certify or repair a broken/missing physical index or arbitrary external corruption. Domain transitions do not manufacture persisted timestamps; API returns actual DB projections. Architecture rationale/applicability belong to [ADR-008](../decisions/tactical-ddd.md); genuine concurrency/runtime acceptance remains tracked independently in NEXORA-027.

## Shared status, strict commands and narrow profile policy

CustomerStatusVO.from rejects unknown/null/undefined/empty/lowercase/non-string status, including corrupt persisted values; it never silently chooses ACTIVE. initial returns ACTIVE; equals compares immutable primitive codes. CREATE still forbids client status, PATCH permits ACTIVE/INACTIVE without new lifecycle restrictions. INACTIVE preserves addresses/readability. Snapshot/persistence serialize the primitive code only. Domain imports pure shared codes, never Vietnamese labels.

All public profile/address create/patch command boundaries reject unknown fields, even alongside valid fields. Ownership/identity/code/default/customerId/statusLabel cannot be mass-assigned. Empty PATCH, null/array/primitive commands reject; phone/country/status policies remain canonical and reused at Application/Domain boundaries.

changeCustomerProfile is the same Domain policy used by Aggregate and the profile-only adapter operation: validate locked persisted status and normalize a strict patch, independent of child state. The adapter retains actor→owner-scoped Customer locks/transaction, selects status without children, applies minimal scoped fields and loads full ordered Detail for response once. It does not fabricate an empty Aggregate, change recipients/default/cardinality, or repair legacy data. Child operations still hydrate full state under locks.

The shared exhaustive CustomerStatusLabelsVi is presentation-only metadata. Presentation adds statusLabel to Summary/Detail responses via one mapper, not Aggregate, VO, persistence or Address responses. See [API contract](../architecture/api-contract.md) for the additive transport field and version assumptions. Same-revision API/Web consumers use shared codes; SDK owns HTTP types. No Customer frontend or new status is implemented.

## Owner-scoped statistics read projection

GET /api/customers includes required stats {total,active,inactive}, all non-negative integers, total=active+inactive. Owner/q/normalized phone scope list and aggregate identically. Status changes list/pagination only; pagination never changes stats. Unknown/empty q and all existing validation/security rules are retained; ADMIN sees only its own population. Successful empty population is0/0/0, distinct from unavailable/error.

This is an Application CustomerPage/CustomerStats projection under ADR-008, without a new aggregate/entity/VO/repository/write operation. Existing aggregate/address/phone/status invariants remain unchanged. Infrastructure uses shared predicates and one grouped database count alongside filtered count/bounded summary, inside existing ACTIVE actor lock/transaction. Existing application writes serialize on that actor; external DBA writes are outside that guarantee. No address hydration/N+1/cache/schema/index or speculative status. Unexpected grouped status returns a safe internal error. DTO/presenter/generated SDK carry the required stats unchanged; Summary/Detail/Address remain unchanged. Frontend cards and their deployed version-boundary behavior remain NEXORA-029 work, not completed here.
