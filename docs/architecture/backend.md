# Backend

`HealthController` maps HTTP to `HealthService`; the application service consumes database/storage health ports. DatabaseAdapter is infrastructure and lazily constructs Prisma so liveness remains available when database operations fail. DB URLs use a 3-second connect timeout in Compose. No AI dependency is required for readiness.
`FilesService` writes the original blob then registers hash/size in the catalog; catalog failure removes the new blob. This is an internal service, with no public upload endpoint. Process crashes between filesystem and catalog writes may leave an orphan; recovery/retention belongs to the ingest milestone. Successful stored files are immutable through the current service.
Config validates required DB URL, canonical absolute storage root, port, node environment and explicit Swagger toggle. Errors expose safe code/message/requestId. JSON HTTP logs contain requestId, status and duration only; headers, query strings, request bodies, cookies, credentials, file contents and notes are excluded by construction. Express trust proxy is configured strictly for trusted internal network hops (loopback, linklocal, uniquelocal); arbitrary forwarded headers from external clients are not trusted. CORS is not enabled.
`AuthController` handles local session lifecycle (`/api/auth/login`, `/api/auth/session`, `/api/auth/logout`) delegating to `AuthService`. Sessions use 32-byte opaque random tokens hashed with SHA-256 in PostgreSQL and transported via `nexora_session` HTTP-only cookies. Login validates body field types before normalization, admission or database work. Username identity is case-sensitive and trimmed consistently with provisioning; valid usernames contain 3–50 characters and Login passwords 1–1024 characters (provisioning requires 8–1024). Invalid fields return 400 VALIDATION_ERROR. Protected business routes enforce global `SessionGuard` registered via `APP_GUARD`, returning 401 UNAUTHORIZED without leaking database internals. Infrastructure health endpoints (`/api/health/live`, `/api/health/ready`) and public auth endpoints (`/api/auth/login`, `/api/auth/logout`) are exempted via `@Public()`. Browser mutations (`/api/auth/login`, `/api/auth/logout`) enforce exact configured Origin through `OriginGuard`; see [configuration](../operations/configuration.md). Missing Origin is forbidden even for internal callers. Expired-session cleanup is executed with isolated error handling to prevent unhandled Promise rejections. Explicit logout uses idempotent `deleteMany`; database failures propagate as safe 500 errors and never produce success or a clearing cookie.

Authentication admission owns bounded process-local state: at most 128 case-sensitive account entries, five failed attempts within a five-minute window, and success clears that account counter. Pending attempts reserve counter capacity synchronously. Before lookup or Scrypt, a global token bucket admits a burst of 10 attempts, refilling one token per second, with at most four concurrent admissions. This permits normal small-instance operator retries while limiting Scrypt CPU and memory during username rotation; rejected requests do not query or hash. Remove expired non-pending entries first, then evict the oldest unlocked/non-pending entry; active locks remain until expiry. If every entry is locked or pending, new accounts receive 429. This intentionally permits temporary denial of new logins under saturation instead of erasing active lockouts. An existing unlocked account may still log in, subject to the global budget. In canonical Docker, client IP may be the proxy/gateway; account keys and the global budget do not assume distinct operator IPs.

Unknown and inactive identities use one precomputed dummy hash generated by the existing `hashPassword` implementation; real Scrypt verification runs before returning the same 401 as wrong credentials. No dummy account exists, and no verification occurs after admission rejection. The compiled trusted CLI (`dist/cli/user-create.js`) delegates provisioning to `identity/infrastructure/user-provisioner.ts`, preserving database ownership and the shared hashing implementation.

## Planned Phase 1 interface amendment

The approved unified foundation uses users/user_credentials/sessions; see [decision](../decisions/unified-identity.md#approved-phase-1-amendment--2026-10-12). Generic session lookup checks ACTIVE user status independently of role or local credentials. Only local password Login requires ADMIN, ACTIVE and a joined Nexora Scrypt credential; provisioning creates both rows atomically. These adaptations are PLANNED, not present in this revision. No new role-gated routes or provider adapter is introduced.
